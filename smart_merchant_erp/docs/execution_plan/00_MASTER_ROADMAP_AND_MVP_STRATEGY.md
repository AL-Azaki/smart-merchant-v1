# الخطة الكبرى الشاملة واستراتيجية الـ MVP لنظام Smart Merchant ERP
## وثيقة المعمارية العليا ودليل التنفيذ للمطور والذكاء الاصطناعي (Master Architecture & Roadmap)

**الإصدار:** 1.0  
**التاريخ:** 10 أكتوبر 2026  
**الهدف:** تحويل المنظومة من نموذج ضخم ومشتت إلى **نظام كاشير، مخزون، وحسابات ذكي ومبسط (Bulletproof Smart Retail ERP)** جاهز للنزول للسوق كـ MVP عالي الموثوقية وقابل للتوسع لاحقاً دون أي إعادة كتابة أو هدم.

---

## 1. الفلسفة المعمارية: كيف ينجح الـ MVP دون الإخلال بالمستقبل؟

### 1.1 مبدأ "المحاسب الخفي" (The Invisible Accountant Pattern)
* **المشكلة:** 90% من تجار التجزئة (محلات مواد غذائية، ملابس، إلكترونيات، صيدليات) لا يفهمون مصطلحات (مدين / دائن / أصول متداولة / حقوق ملكية). إذا أجبرت التاجر على بناء شجرة حسابات وتوزيع قيود، سيفشل النظام ويتركه.
* **الحل:** التاجر يتعامل مع واجهات بديهية جداً:
  1. شاشة كاشير (POS): يبيع نقداً أو آجلاً لعميل.
  2. شاشة مشتريات: يشتري بضاعة ويسجل نقداً أو ديناً لمورد.
  3. سند قبض / سند صرف: يقبض دفعة من عميل أو يسدد دفعة لمورد أو يسجل مصروفاً (إيجار، كهرباء).
  4. شاشة جرد وتسوية مخزون: يعد البضاعة ويسجل الزيادة أو النقص.
* **دور المحرك المحاسبي:** خلف الكواليس، وبشكل آلي غير مرئي، يولد النظام قيوداً يومية مزدوجة متزنة 100% في دفتر الأستاذ العام (`journal_entries` و `journal_entry_lines`).
* **للمحاسب المتقدم:** تتوفر شاشة "القيود المتقدمة" و"شجرة الحسابات الكاملة" لمن يريد إدارة قيود مخصصة.

## 2. مصفوفة تجميد وتسهيل الموديولات (Scope Pruning Matrix)

لتحقيق إطلاق ناجح وسريع، نقسم النظام إلى ثلاث طبقات واضحة:
1. **الطبقة الخضراء (Core Active MVP):** هي قلب النظام الأساسي وتعمل 100%.
2. **الطبقة البرتقالية (Simplified/Automated):** تعمل بطريقة مبسطة تلقائية دون شاشات معقدة.
3. **الطبقة الحمراء (Frozen/Hidden):** مجمدة تماماً في واجهات المستخدم للمرحلة القادمة دون حذف جداول الـ Drift لتجنب كسر قاعدة البيانات.

```
┌────────────────────────────────────────────────────────────────────────┐
│                   طبقة الـ MVP النشطة (Core Active MVP)                │
│  [1. الكاتلوج والمنتجات]  [2. المخزون الموحد]  [3. نقاط البيع POS]       │
│  [4. المشتريات والموردين] [5. الخزينة والصناديق] [6. قيود الأستاذ الآلية]  │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ تغذي آلياً
┌───────────────────────────────────▼────────────────────────────────────┐
│              طبقة التقارير الأساسية (Essential Reporting)               │
│  [كشف حساب عميل/مورد]  [تقرير حركة الخزينة]  [الأرباح والخسائر] [تقييم المخزون]│
└────────────────────────────────────────────────────────────────────────┘
                                    │
                                    X (معطل ومخفي حالياً)
┌───────────────────────────────────▼────────────────────────────────────┐
│             الطبقة المجمدة للإصدار 2.0 (Frozen for Version 2)           │
│  [الأصول الثابتة]  [الموارد البشرية والرواتب]  [مراكز التكلفة المعقدة]     │
│  [التسويات البنكية الآلية]  [مراحل تتبع العملاء CRM]  [الفترات المحاسبية المتعددة]│
└────────────────────────────────────────────────────────────────────────┘
```

### جدول التصنيف التفصيلي للموديولات والجداول:

| الموديول / المجال | الحالة في الـ MVP | الإجراء الهندسي المطلوب | السبب التقني والعملي |
| :--- | :---: | :--- | :--- |
| **Fixed Assets (الأصول الثابتة)** | ❄️ مجمد | إخفاء من القوائم الجانبية والراوتر | التاجر العادي لا يحسب إهلاك الأصول شهرياً؛ هذا يخص الشركات المتوسطة والكبيرة. |
| **HR & Payroll (الموارد البشرية)** | ❄️ مجمد | إخفاء من القوائم الجانبية | مصاريف العمال تسجل كسند صرف مباشر (مصروف رواتب) دون عقود وسجلات دوام. |
| **Bank Reconciliations (التسويات البنكية)** | ❄️ مجمد | إخفاء جداول المطابقة | التاجر يسجل الإيداع والسحب كسند عادي، لا يحتاج مطابقة كشوفات بنكية مستوردة. |
| **Multi-level Periods (الفترات المحاسبية)** | ⚡ تبسيط | الاعتماد على السنة المالية وتاريخ القفل فقط | وجود (سنوات + فترات مالية + فترات محاسبية) معقد جداً؛ تاريخ قفل واحد (`lock_date`) يحمي العمليات السابقة. |
| **Catalog & Products (المنتجات)** | 🟢 نشط | دعم الوحدة الأساسية ومعامل التحويل | قلب النظام؛ التاجر يشتري بالكرتون ويبيع بالحبة. |
| **Inventory (المخزون)** | 🟢 نشط | توحيد الرصيد بالوحدة الأساسية فقط | إلغاء التشتت وتفادي خطأ البيع بالسالب غير المقصود. |
| **Sales & POS (المبيعات)** | 🟢 نشط | بيع نقدي وآجل + مرتجع مبيعات حقيقي | المصدر الأساسي للإيرادات مع طباعة فواتير حرارية و A4. |
| **Purchasing (المشتريات)** | 🟢 نشط | شراء نقدي وآجل + متوسط تكلفة بالعملة الأساسية | ضبط تكلفة المخزون بدقة وتفادي خلط العملات. |
| **Treasury (الخزينة)** | 🟢 نشط | تعدد الصناديق والبنوك + سندات قبض وصرف | إدارة الكاش والشيكات والتحويلات البنكية. |
| **General Ledger (الأستاذ العام)** | 🟢 نشط | توليد قيود متزنة + شاشة قيود يدوية | إثبات كل حدث تجاري بقيد محاسبي مزدوج لا يقبل الخلل. |

## 3. الركائز الهندسية الصارمة (Non-Negotiable Architecture Invariants)

لضمان عدم حدوث أخطاء خفية عند تطبيق الذكاء الاصطناعي للكود، وضعت هذه الركائز كقواعد مطلقة:

### الركيزة 1: مبدأ عملة الأساس الصارمة (Strict Base Currency Engine)
* **القاعدة:** لكل نشاط تجاري عملة أساسية واحدة (`base_currency_id`) يتم تحديدها عند التأسيس (مثلاً: ريال يمني YER أو ريال سعودي SAR).
* **تقييم المخزون:** متوسط تكلفة أي منتج في جدول `inventories.average_cost` يُخزن **حصراً بالعملة الأساسية**.
* **دفتر الأستاذ العام:** جميع سطور القيود اليومية تحتوي على حقلين:
  1. `foreign_amount`: المبلغ بعملة الفاتورة أو السند الأصلية.
  2. `base_amount`: المبلغ محولاً للعملة الأساسية بضرب المبلغ الأجنبي في سعر الصرف (`amount * exchange_rate`).
  3. **القيد المتزن:** يجب دائماً أن يكون `SUM(base_amount WHERE type = 'Debit') == SUM(base_amount WHERE type = 'Credit')`.

### الركيزة 2: توحيد المخزون في الوحدة الصغرى (Base Unit Stock Normalization)
* **القاعدة:** جدول `inventories` يمثل الرصيد الفعلي للمنتج في المخزن، ويجب أن تكون الكمية المخزنة محسوبة دائماً **بالوحدة الأساسية الصغرى للمنتج (Base Unit)**.
* **معامل التحويل (Conversion Factor):**
  * الوحدة الأساسية (مثلاً: حبة) -> `conversion_factor = 1.0`.
  * وحدة العبوة (مثلاً: درزن 12 حبة) -> `conversion_factor = 12.0`.
  * وحدة الكرتون (مثلاً: كرتون 48 حبة) -> `conversion_factor = 48.0`.
* **عند الشراء بكرتون:** 
  * الكمية المضافة للمخزن = `quantity * conversion_factor` (مثلاً: 2 كرتون * 48 = 96 حبة).
  * تكلفة الحبة الواحدة = `unit_purchase_cost / conversion_factor`.
* **عند البيع بحبة أو درزن:** 
  * الكمية المخصومة من المخزن = `sold_quantity * unit.conversion_factor`.
  * وبهذا يستحيل أن يفشل البيع بالحبة إذا كان هناك كرتون متوفر في المخزن!

### الركيزة 3: المعاملات الذرية الشاملة (Atomic Unit of Work)
* لا يمكن تعديل المخزون في جدول، وفشل إنشاء القيد في جدول آخر.
* أي عملية (بيع، شراء، مردود، سند، تسوية جرد) يجب أن تُنفذ بالكامل داخل `ApplicationTransactionRunner.runInTransaction`:
  1. إنشاء رأس الفاتورة وسطورها.
  2. تحديث أرصدة المخزون وحساب متوسط التكلفة.
  3. تحديث أرصدة العملاء/الموردين أو الخزينة.
  4. إنشاء القيد اليومي وسطور القيد المتزنة.
  * في حال فشل أي جزء، يتم التراجع الكامل (Rollback) فوراً.

### الركيزة 4: منع الحذف الصلب بعد الحركة (Strict Immutability & Soft Deletes)
* **ممنوع نهائياً:** حذف حساب في شجرة الحسابات إذا كان مسجلاً عليه أي سطر قيد.
* **ممنوع نهائياً:** حذف عميل أو مورد أو منتج تم استخدامه في فاتورة سابقة.
* **ممنوع نهائياً:** تعديل فاتورة مسجلة ومرحلة مباشرة بالتحديث؛ بل يتم عمل فاتورة مرتجع أو قيد تسوية عكسي.

## 5. مصفوفة الأمور الخفية والمخاطر الصامتة (The Hidden Traps Matrix)

| البند الخفي | كيف يحدث الخطأ دون قصد؟ | الحل الوقائي المحاسبي والبرمجي |
| :--- | :--- | :--- |
| **تقريب الكسور العشرية (Rounding Glitches)** | استخدام `double` في دارت يسبب أرقاماً مثل `10.00000000002`، فيرفض القيد لأنه غير متوازن بـ 0.0001! | استخدام كلاس تقريب مالي صارم (`PrecisionMath.round(val, decimals)`) قبل الإرسال لـ Drift. |
| **تذبذب سعر الصرف بين الشراء والسداد** | التاجر يشتري بضاعة بـ 1000$ بسعر 530 (الذمة 530,000 ريال)، ويسدد بعد أسبوع بسعر 540 (دفع 540,000 ريال). الفارق 10,000 ريال! | توليد قيد آلي لحساب **"فروق أسعار صرف العملات" (Currency Exchange Gain/Loss)** لموازنة القيد. |
| **البيع بالسالب (Negative Stock)** | التاجر يبيع بضاعة لم يسجل فاتورة شرائها بعد بسبب انشغال الكاشير في أوقات الذروة. | توفير خيار في الإعدادات: إما منع البيع بالسالب نهائياً، أو السماح به مع تحذير واعتماد آخر سعر شراء كتكلفة مؤقتة حتى ورود الفاتورة. |
| **مرتجع بضاعة بعد تغيير سعرها** | عميل يرجع بضاعة اشتراها بعرض خاص (خصم 20%)، فيقوم الكاشير بإرجاعها بالسعر الكامل! | ربط فاتورة المرتجع برقم فاتورة البيع الأصلية لاسترداد نفس السعر والكمية ونفس التكلفة التاريخية. |
| **تعديل قيد في فترة سابقة مقفلة** | محاسب أو مستخدم يعدل فاتورة من شهر سابق تم إصدار تقارير أرباحه للشركاء، فتنهار التقارير القديمة! | التحقق الإجباري من حقل `transaction_date >= settings.lock_date` قبل أي عملية إدراج أو تعديل. |

## 6. تعليمات للذكاء الاصطناعي والمطور المنفذ

1. **الالتزام بالترتيب:** لا تنتقل إلى المرحلة 2 قبل إتمام المرحلة 1 وتمرير اختباراتها.
2. **منع الأكواد الوهمية (Zero Mock Tolerance):** أي شاشة تُبنى يجب أن ترتبط بـ Riverpod Providers حقيقية تقرأ وتكتب في الـ SQLite Database.
3. **احترام نمط المعمارية:** الالتزام بطبقات Clean Architecture المعتمدة في المشروع:
   * `domain/`: الكيانات والـ Repository Contracts.
   * `infrastructure/`: تطبيق الـ Repositories واستدعاء الـ DAOs.
   * `application/`: الـ Use Cases وخدمات التنسيق بين الموديولات.
   * `presentation/`: الـ Views والـ Widgets وحالات الـ Riverpod Notifiers (Loading, Error, Data).
